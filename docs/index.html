Python at native speed.

scramjit is a JIT written in pure Python, for the loops the interpreter is slowest at. It turns your hot loop into C, compiles it with cimo in your process and runs it without the GIL: no LLVM, no C compiler, no binary wheels. It runs wherever Python runs, including the browser.

pip install scramjit

Usage

Plain Python in, C out

On the first call scramjit reads the argument types, generates C specialized to them, compiles it with cimo and caches it. Later calls with the same types run native code directly.

  • Still Python. Without the decorator the function runs unchanged in CPython, debuggable and testable as Python.
  • Never changes results. Every compiled function is tested against CPython running it undecorated.
  • No GIL while it runs. Threads calling a compiled function run in parallel.
  • Arrays in place. numpy arrays are passed by pointer, shape and strides, never copied. So are views: m[i], x[a:b], m[:, j].
  • Arrays it makes. np.zeros(n), x.copy(), np.arange and friends compile, freed as the loop goes, and what comes back is an ordinary numpy array.
  • numpy on numbers. np.sqrt(x[i]), np.sin, np.minimum and friends compile, with numpy's result and type. So do x.sum(), x.max() and other reductions.
  • Whole-array arithmetic. a * 2 + b, np.sqrt(a) and m + row compile with numpy's broadcasting and results, each expression one pass with no temporary arrays: faster than numpy in a loop over small and medium arrays.
  • Programs, not only loops. A compiled function can call another: reset, step and policy stay separate functions, and small ones are inlined, so a call costs nothing.
  • C where you want it. k = cimo.compile('...'), then k.mix(x) in a compiled loop: the C goes in the same file, so it's inlined too.
  • Settings in a dict. A dict passed in compiles if its keys don't change, and a loop reading p['k'] runs as fast as one reading a local. So does a constant at module level.
  • Lists as Python's. out.append((i, j)), pop, slices, in, sort and sorted(xs, key=...) compile, on lists that nest and are shared, holding numbers, tuples, arrays, dicts or instances; a returned list is Python's own. So do sets, in CPython's own order, and == and < on all of these.
  • Objects with state. Put @scram on a method of a plain class or dataclass: self.x compiles to a local, self.step(dt) to a call, Vec(x, y) to two variables, a list of them to a list per attribute, and what it writes is on the objects afterwards. Properties and anything else with code of its own stay Python.

import numpy as np
from scramjit import scram

@scram
def edit_distance(a, b, row):
    for j in range(len(b) + 1):
        row[j] = j
    for i in range(1, len(a) + 1):
        prev = row[0]
        row[0] = i
        for j in range(1, len(b) + 1):
            cur = row[j]
            cost = 0 if a[i - 1] == b[j - 1] else 1
            row[j] = min(row[j] + 1, row[j - 1] + 1, prev + cost)
            prev = cur
    return row[len(b)]

from concurrent.futures import ThreadPoolExecutor
import numpy as np
from scramjit import scram

@scram
def mandel_rows(out, y0: int, y1: int, iters: int):
    h, w = out.shape
    for j in range(y0, y1):
        ci = 2.4 * j / h - 1.2
        for i in range(w):
            cr = 3.0 * i / w - 2.0
            zr = zi = 0.0
            n = 0
            while n < iters and zr * zr + zi * zi < 4.0:
                zr, zi = zr * zr - zi * zi + cr, 2.0 * zr * zi + ci
                n += 1
            out[j, i] = n

out = np.zeros((2048, 2048), np.int32)
with ThreadPoolExecutor(8) as pool:   # 8 cores busy, no GIL contention
    for k in range(8):
        pool.submit(mandel_rows, out, 256 * k, 256 * k + 256, 200)

Motivation

Where the interpreter is the bottleneck

numpy is fast when the work fits one array expression. Much real code doesn't: each step depends on the last, or on a branch, or on what was found so far. In CPython every iteration of that loop pays the interpreter, and threads take turns on the GIL.

Where it shines

Loops that don't vectorize

Recurrences, data-dependent branches, flood fills, dynamic programming, simulations, scans over byte buffers. Compiled, they run as C, with the GIL released so threads run in parallel.

y[i] = f(y[i-1])if grid[j][i] == seed:while lo < hi:best = min(best, d[k] + w)
Also a fit

Vectorizable code, pure-Python only

Array math written as plain loops, for places that allow only pure Python or have no numpy. scramjit makes the loop fast without a binary dependency.

Wherever Python runs

Python JITs today bring LLVM or need a C toolchain on the target. scramjit and its compiler are plain Python files, so they go where those can't.

first

Python in the browser

Pyodide, JupyterLite, marimo and PyScript. Existing Python compilers don't run there.

plugins

Embedded Pythons

QGIS, Blender, Houdini, Maya, Nuke, FreeCAD, KiCad: hosts where compiled dependencies are banned or painful.

day one

New platforms

New CPython releases, free-threaded builds and Windows on arm64, before other JITs get there.

libraries

Pure-Python packages

Fast hot paths with no wheel matrix to build, test and release.

Not for: code that is already one vectorized numpy or pandas expression where numpy runs, or anyone already happy with an existing JIT on a standard desktop or server.

How it works

Cold source in, hot code out

Like the engine it is named after, scramjit has no moving parts of its own: the compiler is cimo, and scramjit is the intake that shapes Python into C cimo optimizes well.

1Parse

The function's source, with the standard ast module.

2Infer types

Over the whole function, from the call's argument types and annotations.

3Typed IR

Every value has a concrete C type. No PyObject anywhere.

4Lower

Builtins become loops, lists become arrays, types narrow where proven safe. What can't compile stays Python.

5Emit C

Readable C, with #line pointing back at your Python.

6cimo

Machine code in the process, or WebAssembly in Pyodide.

Builtins are lowering rules, not functions

No builtin exists at runtime. range, zip, enumerate, comprehensions and generator expressions fuse into one loop, and a result is materialized only when stored.

python
total = sum(x * x for x in a if x > 0)
→
c
double total = 0;
for (int64_t i = 0; i < a_len; i++)
    if (a[i] > 0)
        total += a[i] * a[i];

Semantics

Platforms

Supported platforms

The same decorated function runs unchanged everywhere cimo does. scramjit generates the same C; cimo compiles it for the machine it is on.

PlatformCompiled code runs asLoaded with
Linux arm64 / x86-64native arm64, amd64mmap + mprotect (W^X)
macOS, Apple siliconnative arm64MAP_JIT
Windows arm64 / x64native arm64, amd64VirtualAlloc + VirtualProtect
Pyodide, JupyterLite, marimoWebAssemblya side module linked into Pyodide's memory

CPython 3.12 or newer. Compiled code runs with the full privileges of your Python process, like an extension module. There is no sandbox.

Tested: about 3,000 differential tests against CPython and numpy, run in CI on Linux and Windows (x86-64 and arm64), macOS on Apple silicon, CPython 3.12 to 3.14 and free-threaded 3.13, and in part in Pyodide. Pre-release: the API may still change.
